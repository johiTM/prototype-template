# Code Review Process

## Goal

To establish guidelines and checklists for conducting effective code reviews, ensuring code quality, consistency, and knowledge sharing.

## When to Review

- When the designer asks for a review, or after completing a parent task
- Focus on whether the prototype matches the PRD and looks like a real Trackman product

## Review Checklist

### Functionality
- [ ] Code meets the requirements specified in the PRD/task
- [ ] Edge cases are handled appropriately
- [ ] Error handling is implemented
- [ ] User-facing changes work as expected

### Code Quality
- [ ] Code follows project conventions (see `.cursor/rules/stack.mdc`)
- [ ] Code is readable and maintainable
- [ ] No code duplication (DRY principle)
- [ ] Complex logic is commented or self-documenting
- [ ] Variable and function names are clear and descriptive

### Documentation
- [ ] Code is self-documenting or includes comments where needed
- [ ] Complex algorithms or business logic are explained
- [ ] README or documentation is updated if needed
- [ ] API documentation is updated (if applicable)

## Review Process

1. Check the implementation against the PRD — does it cover the required flow?
2. Check the visual output — does it look like a Trackman product, not generic AI output?
3. Flag anything missing or off-brand with a clear suggestion for what to fix
4. Mark items that are nice-to-have vs. blocking

## Review Guidelines

### For Reviewers

**Be constructive:**
- Focus on the code, not the person
- Explain why something should be changed
- Suggest alternatives when possible
- Use "we" language ("we could improve this by...")

**Be respectful:**
- Ask questions rather than make demands
- Recognize that there are multiple valid approaches
- Praise good solutions
- Be timely in responses

**Be thorough but efficient:**
- Don't nitpick every small style issue (use linters for that)
- Focus on correctness, maintainability, and architecture
- Review the whole PR, not just the diff

### For Authors

**Be open to feedback:**
- Code review is a learning opportunity
- Don't take feedback personally
- Ask for clarification if feedback is unclear
- Explain your reasoning when you have a valid alternative approach

**Make reviews easier:**
- Keep PRs small and focused
- Write clear commit messages
- Explain complex decisions in PR description
- Respond to feedback promptly

## Common Issues to Watch For

- **Hardcoded hex colours** — must use `var(--tds-color-*)` tokens instead
- **Wrong background** — page background must be `--tds-color-surface-elevation-0-default` (#f6f6f6), not white
- **Generic-looking UI** — buttons, cards, and typography should match TDS4, not Shadcn defaults
- **Fake mock data** — no "Lorem Ipsum", no "User 1" — data must feel real
- **Dead code** — remove any unused components or commented-out blocks
- **Inconsistent naming** — follow conventions in `.cursor/rules/stack.mdc`

## Issue Categorization

When providing feedback, categorize issues:
- 🔴 **Critical** - Must fix before merging (security, breaking bugs)
- 🟠 **Important** - Should fix (code quality, maintainability)
- 🟡 **Suggestion** - Nice to have (minor improvements)
- 🟢 **Praise** - Highlight good work
